## Is your feature request related to an existing issue?

The catalog and project UI can store MCP server configuration, but the runtime does not yet host or execute MCP servers. The context bar accurately labels that configuration as stored but not executed. The architecture and README need to describe this as deferred rather than present-tense functionality.

## Desired Solution

Design and implement plane-owned MCP execution. Define the supported MCP transport and lifecycle, configuration schema and validation, credential storage and redaction, server-to-agent attachment, tool discovery and policy/gate integration, capture persistence and scrubbing, ACP presentation, and tests using fakes. Preserve the client boundary: Flutter must not own MCP secrets, the canonical transcript, or the tool loop.

The design should settle how project and agent settings compose, what is pinned at `session/new`, and how client-origin tools remain distinct from plane-hosted MCP tools.

## Alternative Solutions

Keep MCP configuration as metadata only until the control-plane lifecycle and security model are defined. Do not introduce client-owned MCP execution as a shortcut.

The current documentation cleanup will mark MCP execution as planned/deferred and link this issue as its implementation home.
